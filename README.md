# んぽ Flight Tracker

个人往返机票价格追踪工具，使用 Next.js。支持按路线、日期范围、停留晚数和航司查询，记录历史价格，并在低于阈值或出现历史新低时发送邮件。

## 本地运行

1. 安装依赖：`npm ci`。
2. 新建 `.env.local`，参考 `.env.example`。如果已经有此文件，请合并缺失配置，不要覆盖已有密钥。
3. 设置至少32字符的随机 `ADMIN_TOKEN`、一个机票服务商的有效密钥，以及搜索条件。建议用密码管理器生成密钥；不要把密钥提交到Git或聊天中。
4. 运行 `npm run dev`，打开 http://localhost:3000，在「管理アクセス」输入管理密钥。
5. 开启邮件前填写SMTP和固定收件人，再设 `EMAIL_ENABLED=true`。页面的测试邮件只发往该收件人。

管理员密钥通过Authorization请求头传输，仅在操作时保留于当前标签页的sessionStorage。历史价格页面可公开查看；搜索、邮件、备份和诊断均需鉴权。未配置管理员密钥时敏感接口返回明确的配置错误。

本地未配置Redis时使用 `data/flights.json`。写入采用文件锁和原子替换，写入失败不会报告成功。命令行 `npm run search` 和 `npm run cron` 与Next.js使用相同的环境文件加载规则。

## Vercel部署准备

在已有Vercel项目添加以下环境变量，并在完成配置后部署：

| 配置 | 用途 |
| --- | --- |
| `ADMIN_TOKEN` | 至少32字符，保护手动搜索及管理接口 |
| `CRON_SECRET` | 独立随机密钥，至少32字符，保护定时接口 |
| `UPSTASH_REDIS_REST_URL`、`UPSTASH_REDIS_REST_TOKEN` | 持久化数据库；可替换为集成提供的`KV_REST_API_URL`、`KV_REST_API_TOKEN` |
| 一个或多个机票服务商密钥 | 获取航班价格 |
| `FLY_FROM`等搜索变量 | 每天自动搜索的路线和条件 |
| SMTP相关变量、`EMAIL_TO` | 发信账号及固定收件人 |
| `EMAIL_ENABLED=true` | 启用邮件 |

可以连接现有的Upstash Redis数据库，也可以通过Vercel Marketplace配置Upstash集成。创建新服务前确认所选套餐与费用；仓库不会自动创建账号或付费资源。生产和预览部署应使用不同数据库，避免测试覆盖真实历史。

Vercel环境没有配置持久存储时会停止搜索并显示错误，不使用临时文件假装保存成功。当前存储采用个人规模的JSON数据集和原子更新；单次Redis请求有9MiB保护上限，超过时会明确报错并要求导出或迁移，不会自动删除历史。长期积累大量查询时应迁移为分表存储。可用`FLIGHT_STORAGE_KEY`区分同一数据库内的不同环境，但生产和预览仍建议使用独立数据库。

本地JSON数据如需迁移，可先通过受保护的 `/api/data-backup` 导出，配置云端存储后再导入；导入会替换整个数据集，操作前先备份目标数据。导入必须通过格式校验。

Vercel定时任务读取 `vercel.json`，当前为每天00:00 UTC（日本时间09:00）。网页显示实际部署时区。`CRON_SCHEDULE`和`CRON_TIMEZONE`只影响本地常驻进程，不会改变Vercel定时。定时接口仅接受 `Authorization: Bearer <CRON_SECRET>`。

## 搜索与通知说明

- Amadeus使用生产环境凭据；`AMADEUS_ENV=test`仅表示测试环境，不参与正式低价监控。
- 请求有总数量和总时间预算。日期分散覆盖用户范围，页面显示实际检查的日期数；结果是抽样中发现的最低价，不是所有日期的穷尽搜索。
- 每次搜索最多保存价格最低的50条已确认结果，仅保存必要元数据。
- 航司筛选严格执行，不用其他航司填充指定航司结果。航段信息不足时不会编造航司或具体返程时间。
- 默认勾选「直行便のみ（乗り継ぎなし）」：去程和返程均须确认直飞，任何一程转机或信息不足都排除，不参与最低价和邮件提醒。取消勾选可包含转机；选择会随搜索条件保存。
- 定时监控也默认仅直飞，可用`NONSTOP_ONLY=false`允许转机。直飞历史与包含转机的历史最低价分别比较；旧记录无法确认直飞时不显示在直飞历史中，但原记录保留。
- 超时时保留已收到的有效结果，标明部分完成和警告。没有有效结果且发生错误时报告失败，不显示“成功、0条”。
- 历史卡片与趋势统计同一路线过往搜索的全部航司，属于历史观察记录；价格和空席需要在预订页面重新确认。
- 相同路线、日期、航司、价格及收件人的通知在12小时内去重。发送失败会释放通知占位，后续可重试。
- 即使历史新低高于通知阈值，首次发送失败后也会在后续查到同一候选时重试。
- 邮件发送失败与搜索结果分开展示，避免把投递失败误报为成功。

## 验证

```sh
npm test
npm run typecheck
npm run lint
npm run build
```

测试使用模拟机票/邮件/Redis响应及临时文件，不消耗真实查票额度或发送真实邮件。生产构建会执行类型和lint检查，不再跳过错误。

上线验收需要实际数据库和服务商配置：确认一次手动搜索写入历史、重新打开页面仍可读取，再检查Vercel定时运行记录和固定收件人的投递结果。仓库测试不能替代实际账号权限、额度和SMTP可达性验证。
